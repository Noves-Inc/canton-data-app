# Contributor note: installation-secret invariants

This note preserves the Helm implementation rules previously embedded in the operator guide. Operator backup and restore policy lives in the [Security model](../security.md#installation-credential-secrets); recovery commands live in the [Helm guide](../helm.md#recover-from-a-kek-generated-by-mistake).

The rules are implemented in [`cda.validate` and `cda.installationSecretValues`](../../chart/noves-canton-data-app/templates/_helpers.tpl), the [KEK Secret template](../../chart/noves-canton-data-app/templates/installation-kek-secret.yaml) and the [backend](../../chart/noves-canton-data-app/templates/backend.yaml)/[frontend](../../chart/noves-canton-data-app/templates/frontend.yaml) templates. [`scripts/test-chart.sh`](../../scripts/test-chart.sh) pins validation, lookup, wrong-restore, recovery and file-permission behavior.

## Secret identity and rendering

- Generated names derive from `cda.fullname`; long names retain a prefix, an eight-character hash and the role suffix within the Kubernetes 63-character limit.
- `installation.kek.existingSecret` and `installation.canary.existingSecret` must be Kubernetes Secret names; their `key` values must be Kubernetes Secret keys. One operator-managed Secret may hold both values only under distinct keys.
- The generated KEK name remains reserved for the KEK and the generated canary name for the capability, even after moving to operator-managed Secrets. Neither role may name its own generated Secret as `existingSecret`: that would remove a mounted Secret from the rendered release. Cross-role reuse could expose the KEK to the frontend.
- `podAnnotations` cannot override `noves.fi/installation-kek-secret`, `checksum/installation-kek` or `checksum/installation-canary`. `backend.extraEnv` cannot override `INSTALLATION_KEK_FILE` or `INSTALLATION_CANARY_CAPABILITY_FILE`.
- Secret values are memoized once per render, so Secret data and pod-template checksums agree. Lookup reuses a generated canary; a missing generated canary Secret/key permits a new value because the capability has no stored state.

## Live-backend evidence and recovery

- The release's live `<fullname>-backend` Deployment names its KEK Secret and records the copied value's checksum. A selected KEK Secret missing its key is a render failure. A selected Secret with a value that differs from the live checksum is also a render failure.
- A missing selected KEK Secret is a render failure while that live Deployment names a KEK Secret or carries a KEK checksum. These checks apply to generated and operator-managed Secrets, including transitions between names or keys; a readable value must remain the same.
- The generated KEK Secret is immutable and retained on uninstall. Kubernetes rejects an apply carrying a different value; restoring over an incorrect value requires deleting and recreating the Secret with the original value.
- If both the selected generated Secret and live dependency evidence are absent, the chart generates a KEK and its notes warn by name. This can occur after uninstall, release/fullname renaming, deletion of both the backend Deployment and KEK Secret, or client-side rendering without lookups. An operator-managed Secret is not generated by the chart.
- A failed backend launched with a newly generated KEK records that new checksum. Selecting the original KEK alone then fails the mismatch guard; deleting only the failed Deployment removes that stale evidence so the next upgrade can restore the original binding. The backend refuses to start if it cannot decrypt the stored credential; generating a different KEK does not recover it.

## File and rollout mechanics

The `installation-secrets` init container runs as the pod's runtime user and copies projected Secrets into a memory-backed `emptyDir` at `/installation-secrets`. It validates the base64 text of 32 bytes (44 characters, no newline), sets owner-only `0600` files and verifies their ownership. The backend user is `1654`; the frontend user is `1000` and never receives the KEK. Application containers mount these copies read-only. The backend is limited to one replica; every frontend replica uses the same canary Secret.

Pod-template checksums roll the consumers when Helm can read changed Secret values. This includes operator-managed Secrets visible to lookup. A client-side renderer cannot obtain those live values; operators supply existing Secrets and restart consumers when changing them outside a Helm upgrade. During a canary rollout the frontend can temporarily receive a refusal until both sides hold the new value; it retries without changing the installation's prior state.
